# 4 个高级 Agent 模式设计方案

按性质分层实现(你已确认):2 个新拓扑 + 1 个中间件 + 1 个横切机制。

## 总览

| 模式 | 层 | 新增文件 | 复杂度 |
|---|---|---|---|
| Plan and Execute | 拓扑(runner) | runners/plan_execute.py | 中 |
| Reflection 反思 | 拓扑(runner) | runners/reflection.py | 中 |
| 摘要/压缩 | 中间件 | middleware/summarization.py | 低 |
| Human-in-the-loop | 横切机制 | gateway HITL + runs 表状态 + 端点 | 高 |

---

## 一、Plan and Execute 拓扑(topology: plan_execute)

**模式**:先用 planner agent 把任务拆成有序步骤列表(返回 JSON),再逐步执行每个步骤(可调度其它 agent 或自己执行)。

**config.yml**:
```yaml
topology: plan_execute
planner: planner_agent          # 规划 agent(产出步骤列表)
executor: task_executor         # 执行 agent(逐个步骤执行);可不填=planner 自己执行
max_steps: 10                   # 最多规划/执行几步(防失控)
recursion_limit: 30
```

**runner 逻辑**(`plan_execute.py`):
1. 调 planner agent,要求它输出 JSON `{"steps": ["步骤1", "步骤2", ...]}`
2. 解析步骤列表(解析失败兜底:把整段输出当单步)
3. 逐步执行:每步调 executor agent(或 planner),前一步输出喂下一步(类似 sequential)
4. 把每步记录到 extra.steps + agent_runs 树

**config 字段新增**(AgentConfig):`planner: str`、`executor: str`、`max_steps: int = 10`

**示例 agent**:`app/ai/agents/research_plan/`(planner 用 deepagents,executor 调用 researcher)

## 二、Reflection 反思拓扑(topology: reflection)

**模式**:执行 → 评估者打分/评判 → 不达标则带反馈重试,达标或达上限则返回。

**config.yml**:
```yaml
topology: reflection
executor: coder_agent          # 执行 agent(产出结果)
evaluator: reviewer_agent      # 评估 agent(评判结果好不好)
max_iterations: 3              # 最多重试几次
pass_threshold: 0.8            # 达标分(评估者返回 0-1 分数;可选,默认看评估者说 pass/fail)
```

**runner 逻辑**(`reflection.py`):
1. 执行 executor,拿结果
2. 调 evaluator:把「任务+结果」给它,要求返回 `{"pass": bool, "score": float, "feedback": "..."}`
3. pass=True → 返回结果;pass=False 且未达 max_iterations → 把 feedback 拼进 prompt 重试
4. 达 max_iterations → 返回最后一次结果(标注「未达标」)
5. 每轮记录到 extra.iterations + agent_runs 树

**config 字段新增**:`executor`、`evaluator`、`max_iterations: int = 3`、`pass_threshold: float = 0.8`

**示例 agent**:`app/ai/agents/coding_loop/`(coder 写代码 → reviewer 审 → 不过则带反馈重写)

## 三、摘要/压缩中间件(name: summarization)

**模式**:对话历史 token 超阈值时,自动用 LLM 把旧历史摘要成一段,避免上下文超限。

**config.yml(任何 agent 都能挂)**:
```yaml
middleware:
  - name: summarization
    config:
      max_messages: 20          # 历史超过 20 条就摘要(默认)
      keep_recent: 4            # 保留最近 4 条不摘要
```

**中间件逻辑**(`summarization.py`,before_invoke):
1. 数 ctx.messages,若 <= max_messages 直接返回
2. 否则:取前面历史(留最近 keep_recent 条),调 LLM(llm.invoke)摘要成一段
3. 用摘要 + 最近 keep_recent 条替换原历史
4. after_invoke 不做事(只读压缩)

**复用**:走 `app.services.llm`(同一个 provider),不依赖后端。与 session_memory 配合:session 存原始消息,summarization 在喂给模型前压缩。

## 四、Human-in-the-loop 横切机制(最复杂,分两期)

**核心难点**:deepagents 用 LangGraph interrupt + Command(resume) + checkpointer(我们没配);agentscope 用事件 + reply 重调。两库机制完全不同。

### 务实设计:统一「暂停点」+ HTTP 确认 API(不碰库内部机制)

**不依赖库的 interrupt**:在 gateway 层做暂停——配置里声明「哪些工具调用需要人确认」,后端执行**前**检查,命中则暂停(返回 pending 状态),人确认后用「确认/拒绝」决策重新调用。

**config.yml(任何 agent)**:
```yaml
hitl:                          # 横切配置(不属于 middleware,在 agent 顶层)
  tools: ["send_email", "delete_record"]   # 这些工具调用前要人确认
  auto_approve_others: true                # 其它工具自动放行
```

**AgentConfig 新增**:`hitl: HITLConfig`(tools + auto_approve)

**gateway 新增方法**:
- `trigger/chat` 检测到 hitl 工具被调用时,不执行,而是:
  - 写一条 agent_runs(status=awaiting_confirmation),存「待确认的工具调用」
  - 返回特殊结果 `AgentResult(output="", pending_confirmation={...})`
- `confirm(run_id, decision)` 方法:批准/拒绝/编辑参数,然后用决策重新触发执行

**新增端点**:
- `POST /agents/{name}/runs/{run_id}/confirm` — body: `{decision: "approve"|"reject"|"edit", args: {...}}`

**两库适配**(backends):
- deepagents:在 `_to_lc_tool` 包一层,工具执行前查 hitl 配置;或用库的 `interrupt_on` + 配 checkpointer(更地道但复杂)
- agentscope:`is_read_only=False` 让它走权限询问,捕获 `RequireUserConfirmEvent` 后挂起

**第一期务实版**(本次实现):gateway 层的「工具执行前拦截」+ confirm 端点。不依赖库内部 interrupt 机制(避免 checkpointer 复杂度),够用且统一。
**第二期**(后续):接 deepagents 原生 interrupt_on + checkpointer 做更地道的 LangGraph 式暂停。

## 设计取舍

- **plan_execute/reflection 复用 run_member**:和 pipeline 一样,执行者/评估者通过 run_member 回调跑,自动写树状记录。
- **summarization 走 llm.invoke**:不绑后端,任何 agent 都能挂(中间件层)。
- **HITL 第一期务实**:gateway 层拦截而非库原生 interrupt,避免 checkpointer 依赖,保证两库统一 + 跨拓扑可用。代价:暂停粒度在「工具调用前」而非「任意时刻」——对绝大多数审批场景够用。
- **config.yml 扩展**:每个模式加自己的字段(planner/executor/max_iterations/hitl 等),不互相干扰。
