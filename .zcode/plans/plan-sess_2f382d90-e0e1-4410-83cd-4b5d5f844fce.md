# 文档智能审核方案（修订：双输入源）

## 核心修正：检查项有两个输入源

每个检查项同时需要：
- **OCR 文档内容**（从 url → MinerU 得到）：错别字、标题结构、表格、公章位置等
- **entity 业务数据**（外部系统直接传入）：人名、项目、供应商名等比对基准

例：检查「校对人≠批复人」→ 需 entity 里的预期人员 + OCR 文档里实际填的人员，两者比对。
检查「公章名=供应商名」→ 需 entity 里的供应商名 + OCR 文档里识别出的公章文字。

## 数据流

```
POST /api/v1/doc-review
  body: {
    entity: {project, supplier_name, expected_reviewer, expected_approver, ...},  ← 业务数据(比对基准)
    url: "https://.../file.pdf"                                                    ← 文档地址
  }
  ▼
① 下载文件 + MinerU OCR + 排序恢复 → doc_content(结构化文档 markdown)
  ▼
② 并行检查(每项同时拿 doc_content + entity):
   规则类:公章红色(entity 供应商名 vs OCR 公章文字)、人名比对(entity 人员 vs OCR 填写)
   AI 类:错别字(OCR 文档)、标题完整性(OCR 文档 vs entity 模板信息)、表格(OCR 文档)
  ▼
③ 汇总报告 → 结构化审核结果 JSON
```

## 关键设计：entity 怎么传到各检查项

pipeline 现有机制是「步骤输出文本喂下一步」。但 entity 是贯穿全程的基准数据，不能只靠步骤间文本传递。方案：

**在 doc_review service 里**：
1. 入口把 entity 存为本次审核的「上下文基准」
2. 构造每个检查 agent 的 prompt 时，把 entity 关键字段 + OCR 文档内容一起拼进 prompt
3. 不用纯 pipeline 拓扑（它只在步骤间传文本），改用 **service 层编排**：service 拿到 entity + OCR 结果后，显式组装每个并行检查的输入

### 两种实现路线对比

| | 路线 A:service 编排 | 路线 B:pipeline 拓扑 |
|---|---|---|
| entity 传递 | service 直接注入每个检查的 prompt | 需 hack 步骤间传 entity(不自然) |
| OCR 结果传递 | service 拿到后注入 | step1 输出 → step2 输入(自然) |
| 并行检查 | service 用 asyncio.gather | pipeline 的 parallel step(自然) |
| 适合度 | ✅ 双输入源场景更自然 | ⚠️ 单输入链式场景更好 |

**选路线 A（service 编排）**：因为双输入源（entity + OCR）用 service 显式组装更清晰，pipeline 的单链传递反而别扭。service 内部仍复用框架的 agent_gateway 触发各检查 agent + 用 asyncio 做并行。

## 实现拆解（6 部分）

### 一、入口端点 + service（编排核心）

`app/api/v1/endpoints/doc_review.py`：
```
POST /api/v1/doc-review
  body: {entity: {...}, url: "...", callback_url?: "..."}
  返回: {review_id, status: "processing"}
```

`app/services/doc_review.py`（service 编排）：
```python
async def run_review(entity: dict, url: str, review_id: str):
    # ① OCR + 排序
    doc_content = await agent_gateway.trigger("doc_ocr_sorter", url, source="api")
    # ② 并行检查:每项拿 doc_content + entity
    checks = {
        "typo":           ("typo_checker", build_prompt(doc, entity, "检查错别字")),
        "heading":        ("heading_checker", build_prompt(doc, entity, "检查标题完整性")),
        "table":          ("table_checker", build_prompt(doc, entity, "检查表格")),
        "seal":           ("rule_seal_checker", build_prompt(doc, entity, "检查公章")),
        "signer":         ("rule_signer_checker", build_prompt(doc, entity, "检查校对人/批复人")),
        "cover":          ("cover_checker", build_prompt(doc, entity, "检查封面规范")),
        # ... 十几项
    }
    results = await asyncio.gather(*[
        agent_gateway.trigger(agent, prompt) for agent, prompt in checks.values()
    ])
    # ③ 汇总报告
    report = await agent_gateway.trigger("review_reporter", format_results(results, entity))
    # 回调
    if callback_url: await http_client.post(callback_url, json=report)
```

`build_prompt(doc_content, entity, task)`：把 OCR 文档 + entity 业务数据 + 检查任务拼成 prompt。entity 里的人名/供应商名等作为比对基准明确告知 agent。

### 三、规则检查工具（纯代码 @tool，快且准）

`app/ai/tools/doc_rules.py`：
```python
@tool("check_red_seal")        # 红色公章检测(基于 OCR 返回的颜色/图片信息)
@tool("check_name_conflict")   # 校对人 vs 批复人是否同一人(传两个人名)
@tool("check_seal_supplier")   # 公章文字 vs 供应商名是否一致
```
这些是确定性代码判断，agent 调用时拿结果，不耗 LLM token。

### 四、各检查 agent（AI 类 + 规则类）

每个 checker 是 single 拓扑 + deepagents（深度推理）：
- `doc_ocr_sorter`：调 mineru_ocr 工具，恢复乱序页面
- `typo_checker`：找错别字
- `heading_checker`：对照 entity 模板信息检查标题完整性
- `table_checker`：判断表格结构
- `cover_checker`：封面等级信息规范
- `rule_seal_checker`：调 check_red_seal + check_seal_supplier 工具
- `rule_signer_checker`：调 check_name_conflict 工具
- `review_reporter`：汇总所有检查结果生成报告

AI 类 agent 的 prompt 由 service 注入（含 OCR 文档 + entity 基准）；
规则类 agent 调工具拿结果（工具参数由 agent 从 prompt 里的 entity/OCR 信息提取）。

## 后端选型（明确回答你的问题）

| 环节 | 后端 | 原因 |
|---|---|---|
| OCR+排序、AI检查、汇总 | **deepagents** | 深度推理+规划+文件系统 |
| 规则检查(公章/人名) | **规则代码 @tool** | 确定性,快准省 |
| 编排(并行/汇总) | **service 层 asyncio.gather** | 双输入源用 service 显式组装最清晰 |
| agentscope | **本场景不用** | 无多 agent 对话协商需求 |

agentscope 仅在将来「多审核员讨论争议项」时才用 conversational 拓扑。当前场景全 deepagents + 规则代码 + service 编排。

## 落地顺序
1. config 加 mineru/doc_review 段
2. mineru_ocr 工具 + doc_rules 规则工具集
3. 各 checker agent（AI 类用 deepagents）
4. doc_review service（编排核心：OCR→并行检查→汇总）
5. doc_review 端点（接收 entity+url，异步触发，回调）
6. 测试（stub OCR + 真实 LLM 验证）

## 复用框架能力
- agent_gateway 触发各 checker agent（自动树状记录、可观测）
- @tool 工具系统（MinerU OCR、规则检查）
- http_client（下载文件、调 MinerU、回调）
- deepagents（深度推理检查）
