> 依据：《CPS智能巡检系统PRD.md》v1.3（920 行，FR-01~FR-22、AC-01~AC-34）及现有工程核验（`cps/` Java 业务+管理台+移动端；`basic-project/` Python Agent 服务）

## 0. 文档说明与总体假设声明

1. 本计划覆盖 PRD v1.3 **全部已确认功能**。PRD 第 33.1 节明确："本 PRD 全部已确认功能一起交付……第 14 节历史 MVP 分期仅作历史规划，不再作为将已确认功能延期或排除的依据"。因此第 14 节的 MVP/二三阶段划分**不作为分期依据**，本计划为一次性全量交付。
2. PRD 中标注"建议""待细化"的内容**不自动升格为已批准需求**（PRD 18.1、33.1）。本计划涉及建议项时均显式标注，不将其当作确认范围排期，仅按技术设计需要预留工作量。
3. PRD 第 27 节（9 项）、第 32.2 节（5 项）、第 17 节（8 项）待确认事项**不得擅自当作已确认**。全部纳入第 8 节「决策清单」管理，标注建议决策时点；未关闭前按"可并行暂定、验收前必须关闭"原则处理。
4. 【假设】团队配置、人力到岗时间、有效开发日历（每周 5 个工作日）均为计划假设，见第 4.1 节；假设不成立时按第 7 节排期风险流程调整基线。
5. 本计划本身不构成开发授权。按 PRD 18.1"本轮仅形成 PRD，不授权开发、部署"，启动开发与部署需用户批准本计划后进行；上线切换（旧单/新单分流时点）需用户确认（见决策清单 D-01）。
6. 现状核验结论（作为排期输入）：
   - `cps/backend`（Spring Boot + MyBatis + Flyway）已有 `CpsAgentFrameworkClient`、`CpsIssueService`、`CpsWorkflowStateMachine`、`RustFsStorageService`、Milvus 向量与图片 embedding 等服务；`cps/admin`（React 管理台）与 `cps/mobile`（React 移动端）已有页面骨架。
   - `basic-project`（FastAPI）已有 `app/api/v1/endpoints/cps.py`、`agent_runs.py`、`app/core/scheduler.py`、alembic 迁移、`tests/cps/`（business/integration/recovery/workflow 测试）；`skills/` 目录存在但为空（报告 Skill 需从零新建）。
   - 与 PRD 26.1 的判断一致：已有适配入口 ≠ 接通。**整改同步、结果回写、计划建单、附件可靠性均未证实接通**，故设 Phase 0 前置核验。

## 2. 前置核验阶段（Phase 0）

**定位**：PRD 26.1 明确"附件传递可靠性和真实接口联调是前置核验事项；不能以移动端 mock 回退结果作为验收证据"；32.2-5 明确"旧系统兼容性测试的数据范围和接口清单需技术核验"。Phase 0 的产出直接决定 P1/P3/P4/P9 的实际工作量，是全计划的第一道闸门。

**周期**：第 1 周～第 1.5 周（W1–W1.5）；与架构设计评审并行。

### 2.2 Phase 0 退出准则

1. 《前置核验报告》评审通过，接通缺口已转化为 P1/P3/P4/P9 的任务或风险条目；
2. 附件通道在联调环境验证通过（或明确阻塞项及 workaround 与责任方）；
3. 旧单/新单切换方案获架构师会签、用户确认（D-01）；
4. 决策清单中"开发前必须关闭"项（D-01~D-04）全部关闭；
5. 交付基线（第 1 节）冻结，此后范围变更走书面变更流程。

【假设】Phase 0 发现的重大缺口（如回写通道需完全重建）不超 P1/P4 估算的 +30%；超出则触发第 7 节 R-13 重排基线。

### 8.3 决策管理机制

- 决策会节奏：M0 决策会（A 类集中关闭）+ 每迭代评审会附带 B 类项过堂；PM 维护清单状态（未决/暂定/已关闭）。
