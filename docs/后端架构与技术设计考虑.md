**职责切分原则**（PRD 26.1）：
- **Java 库 = 业务事实的唯一真相源**：问题单、整改提交版本、初审任务与意见（供审核台）、巡检计划与业务任务、辅房/点检/台账、事项权限与审核员配置。业务状态机、权限、审计流转归 Java。
- **Python 库 = AI 执行与运行时**：Agent 编排（既有 7 对象运行态）、初审执行记录（模型版本/耗时/错误）、周报运行记录与文件、长期记忆、语音转写。
- **跨库只通过 API 交换业务 ID 字符串**（如 `cps_issue.agent_inspection_id` 既有模式），**禁止跨库外键、禁止 Java 直连 PG / Python 直连 MySQL**。

### 2.2 Java 库新增/改造表（Flyway）

**（a）`cps_issue` 改造（§28.1/28.2）**
- 新增列：`short_term_measure VARCHAR(1000)`、`long_term_measure VARCHAR(1000)`（保留 `corrective_measure` 兼容旧单只读）；`current_submission_version INT NOT NULL DEFAULT 0`；`inspection_item_id BIGINT NULL`（巡检事项，30.1）。
- 状态机扩展（`CpsIssueStatus` 新值，旧值保留）：
  - `PENDING_RECTIFY`（整改办理中：可编辑/暂存/转办）
  - `PENDING_AI_REVIEW`（已提交、AI 初审中，版本锁定）
  - `PENDING_REVIEW`（待审核专员裁决；AI 完成、失败可接管或超时可接管均落此态并附初审任务状态）
  - `PENDING_REVIEWER_CONFIG`（缺审核员配置，保留提交待配置，30.2/AC-25）
  - `CLOSED` / 退回→`PENDING_RECTIFY`
- **旧单兼容（AC-34）**：以"单创建时间 + 流程版本"切分，存量未完成单沿用 `PENDING_FEEDBACK/PENDING_UPLOAD_PROOF` 旧链路直至办结，不做强制迁移（33.1）。

**（b）`cps_rectification_submission`（§28.3 提交版本）**
`id, issue_id, version_no, reason, short_term_measure, long_term_measure, responsible_emp_no/name（责任员工快照）, attachment_ids JSON, submitted_by, submitted_at, source(SUBMIT/RESUBMIT), status(LOCKED/REVIEWED/SUPERSEDED), created_at`；`UNIQUE(issue_id, version_no)`。暂存不生成版本（写 issue 草稿字段）；提交时快照 + `version_no++` + 锁定；退回重提生成新版本并必触发新初审（AC-26）。

**（c）`cps_rectification_transfer`（§28.3 转办）**
`id, issue_id, version_no NULL, from_emp_no, to_emp_no, transferred_at, remark`。转办后仅 `current_handler_emp_no` 办理并接收退回，原办理人失权；责任员工不变。

**（d）`cps_initial_review_task`（§28.4，三态核心）**
`id, issue_id, submission_id, version_no, status ENUM(RUNNING/FAILED/TIMEOUT_OPEN/COMPLETED/TAKEN_OVER/LATE_RESULT), submitted_at（计时起点=提交成功时刻）, timeout_at(=submitted_at+600s), completed_at, taken_over_by, taken_over_at, takeover_reason（必填）, error_code, retry_count`；`UNIQUE(issue_id, version_no)`。
> 语义（AC-27）：RUNNING 未满 10 分钟不得开放接管；满 10 分钟 → `TIMEOUT_OPEN`（≠失败）；Python 显式失败 → `FAILED`（立即可接管）；接管后迟到 AI 结果 → `LATE_RESULT` 仅留痕，不覆盖人工裁决、不重复流转。

**（e）`cps_initial_review_result` + `cps_initial_review_item`（§29.3）**
主表：`id, task_id, submission_id, version_no, overall(PASS/PARTIAL/PROBLEM——仅意见，无决定权), model_status, is_late, created_at`。
明细：`id, review_id, check_type(IMAGE_COMPARE/MEASURE_SIMILARITY/TEXT_VALIDITY/TEXT_LENGTH/PUNCTUATION_RATIO), field_name(reason/short_term/long_term), verdict(PASS/FAIL/WARN/SKIPPED), text_length L, punctuation_count P, ratio_ok, reason, problem_fragment, evidence_refs JSON, confidence`。
> 部分检查缺失记 `SKIPPED` + `PARTIAL`，不得伪造通过（28.4）；审核专员可查看原内容与逐项意见（29.3）。

**（f）`cps_inspection_plan` + `cps_inspection_plan_item`（§22）**
计划：`id, plan_no, source_report_type, source_run_id（字符串关联 Python 周报运行）, title, objective, risk_basis, status(DRAFT/PENDING_APPROVAL/APPROVED/CANCELLED), approval_batch_no, approved_by/at, created_at`。

**（g）辅房域（§23-24）**

## 3. 关键后端机制

### 3.1 AI 初审异步任务管线（§28-29；AC-16/17/18/27）

**选型**：**任务表 + 内嵌异步执行，不引入独立 MQ**。理由：整改提交频率低（日百级）、分钟级时延容忍、现有 `app/tasks` + FastAPI 后台任务通道已够用；引入 RabbitMQ/Redis Stream 的运维成本大于收益。以 `cps_initial_review_task`（Java）为唯一状态真相源，Python 无状态执行，接口抽象为 `InitialReviewTransport`（submit/查询/回调），未来可平滑替换为 MQ。

**管线时序**：
1. 整改人员提交（Java 事务）：创建 submission v_n（锁定）→ issue 状态 `PENDING_AI_REVIEW` → 创建 task(`RUNNING`, `submitted_at=now`, `timeout_at=+600s`) → 事务提交后投递 C-01（202）。
2. Python 执行：**确定性规则先行**（§3.4 字数/标点纯代码计算，毫秒级）→ 视觉比对（前后图片）与语义检查（雷同性/有效性）并行调模型 → 汇总为结构化意见 → 回调 C-02 回写 Java。
3. Java 定时扫描（30s 周期）：`RUNNING && now ≥ timeout_at` → `TIMEOUT_OPEN`（开放接管，界面三态：运行中/执行失败/超时可接管，28.4）。
4. 失败路径：投递失败（连接拒绝/5xx）或执行异常回调 → `FAILED`（含 error_code）→ **立即可接管**，不等 10 分钟。
5. 技术重试：网络/超时类自动重试 ≤2 次（30s/60s 退避）；**重试不重置计时**（计时以首次提交成功为准，28.4"每次重新提交的初审独立计时"）；业务性失败不自动重试。
6. 接管：审核专员在审核台发起 → task `TAKEN_OVER`（taken_over_by/at/reason **必填**）→ 直接人工裁决（通过关闭/不通过退回），"接管不是自动关闭"（28.4）。
7. 迟到结果：回调到达时 task 已 `TAKEN_OVER`/人工已裁决 → 意见存 `is_late=true` 留痕，不改状态、不推进流程（AC-27）。
8. 模型预算：单视觉调用超时 60s、语义 30s；整任务 wall-clock 强制 8 分钟（<10min 留接管余量）到点中断并标 `FAILED`（§16 调用链控制）。

### 3.2 幂等键设计（§5.5/§13/§22；AC-30）

统一规范：`{domain}-{entity}-{natural-key}[-{version}]`，**数据库唯一索引兜底，重复请求返回既有结果并校验参数一致**：

| 场景 | 幂等键 | 落点 |
|---|---|---|
| 初审任务创建 | `cps-rectify-{issueId}-v{n}` | Python 执行侧 + Java task UNIQUE(issue_id,version_no) |
| 初审结果回写 | `initial-review-result-{taskId}` | Java 回调端去重 |
| 周报运行 | `weekly-{type}-{period_start}` | `weekly_report_run.idempotency_key` UNIQUE |

### 3.3 定时调度：分类周报（§21.1；AC-28/29）

- **执行器**：复用 `app/core/scheduler.py` 的 `@scheduled(cron="0 8 * * MON", misfire_grace_time=...)`。两个硬性注意：① APScheduler 必须显式 `timezone="Asia/Shanghai"`（容器 TZ 不可靠）；② 当前单实例部署，多实例需加分布式锁（记为扩展约束）。
- **窗口**：以东八区计算 `period_end = 本周一 00:00`、`period_start = period_end − 7d`，左闭右开 `[start, end)`，比较业务时间字段（`check_time`/`submit_time`）时统一"东八区计算 → 转 UTC 存/比"。
- **分类各自生成**：巡检分类清单配置驱动（§27.4 待确认——先落 CPS 问题巡检、辅房点检两类已知，配置表可扩展），每类型独立运行记录与文件。
- **重跑策略**：幂等键防同周期重复；`GENERATE_FAILED/UPLOAD_FAILED` 自动重试（阶梯间隔，上限 3 次）；手动重跑生成**新版本文件**（object key 带 run_no，不覆盖历史运行记录——版本保留策略待确认 §27.4）。
- **漏跑补偿**：启动时扫描"当天应为周一 08:00 之后且无该周期记录"的类型补跑（misfire 补偿），补偿也走幂等键。
- **无需人工审核**：周报生成→上传→归档→进入推送流程全自动（21.1.7 例外条款）；推送适配器为接口 registry，未注册渠道 → `push_status=UNCONFIGURED`，界面显示"推送未配置"。

### 3.4 文本规则确定性计算（§29.2；AC-17/24）——必须代码实现，禁模型估算

Python 纯函数 `check_text_rules(text) -> {L, P, length_ok, ratio_ok, no_consecutive_punct, verdict}`，要点：

1. **字符计数**：按 Unicode code point（Python `str` 天然）；换行集合 `{\n, \r, \u2028, \u2029}` 剔除后得全文 S；`L = len(S)`，**空格计入 L**（29.2.1）。
2. **标点集合**（技术设计统一定义并固化为常量表 + 单测）：中文标点（，。、；：？！""''（）【】《》—… 等）+ 英文标点（,.;:?!'"()[]{}- 等）+ **空格（半角 U+0020 必算；全角 U+3000 建议同算并在口径文档记录**）。`P` = 出现次数（非种类数，29.2.2）。
3. **`……` 例外**（29.2.3）：显式状态机扫描——遇 U+2026 且下一字符亦为 U+2026 → 整体消耗，`P += 1`，不计连续标点；其**在 L 中按实际字符数计量**（两个 U+2026 → L 贡献 6）；单个 U+2026 出现 → 也计一个标点。不得把一切重复标点折叠，只有"……"整体享有例外。
4. **连续标点**：扫描 S 相邻两字符均属标点/空格类 → 违规（`， 。` 中间的空格属标点类，故算连续，不能靠插空格绕过，29.2.6）；合法 `……` 已被整体消耗不触发。
5. **判定**：`length_ok = (L >= 15)`；`ratio_ok = (10 * P <= L)`（**整数精确比较，防浮点与舍入**，29.2.8；L=0 时 0≥15 为假且无除法，天然避免除零）；`no_consecutive_punct`；三字段（原因/短期/长期）**分别独立计算，禁止合并凑字数**（29.1）。
6. **边界用例固化单测**（29.2 示例 + AC-17/24）：`L=15,P=1`✓；`L=15,P=2`✗；`L=20,P=2`✓（恰 10% 满足，不得四舍五入放宽）；`L=14,P=0`✗；空文本 ✗；`， 。` 连续标点 ✗；`……` P=1 不违规。
7. **落库**：L/P 实际值随意见明细存 `cps_initial_review_item`（29.2"记录实际值"），供审核专员核对。
8. 语义类检查（无意义/敷衍文字、措施雷同）由模型承担，输出意见片段与理由（19.2/29.1），**同样只出意见不直接退回**（29.1 末段）。

### 3.5 库存事务（§25；AC-33）

- 出入库单 DB 事务：`SELECT ... FOR UPDATE` 锁 `cps_inventory_item` 行 → 校验出库 `quantity ≤ stock_before`（**禁负库存**）→ 更新 `stock_qty` → 插入 movement（含 before/after 快照）→ 预警评估 → 提交。DB `CHECK(stock_qty>=0)` 兜底。
- 预警评估（同事务读新值）：`stock_after ≤ alert_qty`（**等于阈值也触发**，AC-13/33）→ upsert `ACTIVE` 事件（同 item+room 已有 ACTIVE 则合并不新建）+ 投递通知任务；`stock_after > alert_qty` 且存在 `ACTIVE` → `RESOLVED`。再次不足 → 新事件。
- 通知：发送渠道待确认（§27.8）→ 通知端口抽象 + `notify_status` 记录（对齐周报"未配置不伪造成功"模式）；合并期内节流（建议每日 ≤1 次，待确认）。

### 3.6 提交锁定与版本化（§28.3；AC-26）

- **整改单**：编辑/转办门禁 = 状态 ∈ {`PENDING_RECTIFY`（办理中/退回整改）}；提交 → 事务内生成 submission 快照 + `version_no++` + `PENDING_AI_REVIEW` 锁定（AI 初审中/待人工审核不得修改或转办该版本）；退回重提 → 新版本 + 必触发新初审，旧版本意见不覆盖新版本（意见挂 submission_id）。
- **辅房点检单**：DRAFT 期间本人可修正有效图片的判定（PASS/FAIL 均可改，记录 AI 原始值/修改人/时间/原因）并按最终结果重算当前得分；SUBMIT → 终态计分 + 锁定，其他人不可改、无管理员重开（24.2、AC-10/23）。
- 实现：状态字段门禁 + 乐观锁（version/updated_at）双保险，拒绝并发双写。

## 4. 文件与存储

- **RustFS 复用边界**（26.1）：沿用现有 S3 兼容服务（:9000）。业务上"用已有存储组件"不等于上传/运行记录/下载已实现——本轮补全链路。
- **对象组织**：
  - 问题证据：`cps-issues/{issueId}/before|after/{attId}.{ext}`
  - 点检照片：`room-checks/{submissionId}/{itemId}-{attempt}.{ext}`（重拍新 attempt，保留 AI 判定依据）
  - 周报：`weekly-reports/{type}/{yyyy-Ww}/{run_no}.html`（run_no 天然版本化，重跑不覆盖）
  - 语音（若保留原音）：`speech/{date}/{request_id}`（保留周期待确认）
- **受控下载**（21.3）：文件地址一律存 **object_key 受控引用**，不生成公开链接。周报下载链路：admin → Java C-08（校验登录 + 权限 + `status=ARCHIVED`）→ Java 经 internal_trust 调 Python C-05 取流（或短时效预签名 URL）→ 流式返回。问题照片同理按单据权限过滤。
- **一致性对账**：运行记录 ↔ object_key 定期对账 job（孤儿文件/缺文件告警）；RustFS 数据卷备份策略随部署方案定。

## 5. 安全与权限

- **角色矩阵落地**（§3 → §28/30 细化）：在 `cps_admin_user` 角色体系中明确：巡检员工（稽查人）、整改人员、审核专员、拉线主管、巡检管理员、系统管理员。Java 接口注解式鉴权；Python 侧 Identity 校验（既有 auth）。
- **事项权限（30.1，以事项为中心）**：可选项查询 SQL 语义 = `SELECT i FROM cps_inspection_item i WHERE i.enabled AND (NOT EXISTS(permission p WHERE p.item=i) OR EXISTS(p WHERE p.item=i AND p.emp=:me))`。**严禁人员侧反推**（"人员未配置≠全量开放"，AC-19）。
- **审核员路由（30.2）**：问题提交时查 `item×factory → reviewer`；缺失 → `PENDING_REVIEWER_CONFIG` + 管理员提醒（渠道待确认），配置完成后继续流转、不要求重新提交（AC-25）；管理员改配 → 未完成审核单批量转新审核员 + 变更日志，已完成不改写；不跳过审核、不自动指派他人、禁备用审核员。
- **Agent/工具白名单**（5.5.3/6.1/16）：人工改派候选 = Agent 白名单 ∩ 用户权限（既有 `/cps/agents` catalog + config agents.yaml）；专用 Agent 只读数据（经服务 API/只读副本），**不直写生产业务表与长期记忆**（6.1）；无权限工具调用一律拒绝并留痕。
- **网络边界**：Java↔Python 沿用 `internal_trust + trusted_networks`（README-AGENT-INTEGRATION 既有约定），K8s 用 NetworkPolicy 收敛到 CPS 命名空间；网段外强制 JWT。移动端/管理台不暴露 Agent、模型与原始 JSON。
- **审计**：`cps_issue_flow_log` 扩展记录 AI 初审触发/结果/接管/裁决事件；Python 侧事件流（既有 SSE `/events`）+ `agent_initial_review_exec` 双向可拼，统一 trace 贯穿（trace_id = issueId 或 submission_id）。
